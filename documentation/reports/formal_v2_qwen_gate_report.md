# Formal v2 Qwen2.5-VL 闸门测试报告

## 1. 测试目的

本次测试用于确认`formal_v2`扩展轨道在Qwen2.5-VL-7B-Instruct 4-bit配置下能否完成真实推理，重点检查多图解析、16K长上下文、固定历史回放、输出截断和显存占用。闸门集仅包含12条样本，不用于估计正式安全指标。

运行配置为`configs/runs/formal_v2_qwen_gate.json`。其中包含8条MMDS风险样本和4条MMDU良性样本，覆盖四类风险、自然/2K/8K/16K文本长度以及两组良性多图长上下文对照。扩展轨道使用`fixed_reference`模式，前置助手回答来自来源数据，待测模型仅生成最终轮回答。

## 2. 运行结果

| 项目 | 结果 |
|---|---:|
| 样本数 | 12 |
| 对话轮次总数 | 42 |
| 实际模型生成调用 | 12 |
| 成功样本 | 12 |
| 失败样本 | 0 |
| 输出截断 | 0 |
| 最大实际输入token | 18,741 |
| 最大输出token | 283 |
| 峰值GPU显存 | 9,355.03 MiB |
| 总生成耗时 | 97.78 s |

16K文本条件的实际输入约为17,083至18,741 tokens。差值主要来自图像token、聊天模板、系统提示和回答约束，因此正式实验必须记录模型处理器返回的真实输入token，不能只使用构建阶段的空白分词估计。

良性样本在2K至16K条件下均生成了与图像问题相关的正常回答，未出现明显的安全拒答。风险样本也均完成推理，但闸门测试不根据表面拒答词直接判定攻击是否成功；部分回答需要结合完整风险意图和操作性细节进行人工标注。这再次说明正式结果应采用既定的双人标注与仲裁流程。

## 3. 结论与后续顺序

当前数据和运行框架已通过16K、多图、固定历史模式的资源闸门，可以进入分片正式实验。建议依次运行MMDS自然长度、2K、8K和16K分片，再运行MMDU的2K、8K和16K分片。每个分片使用`--resume`保留断点，并在进入下一长度档前检查失败数、真实输入长度和截断数。

本次首次运行补齐了本机Hugging Face缓存中的5个Qwen2.5-VL权重文件。后续在同一环境中可直接复用缓存；若在受限沙箱中运行，仍需允许访问用户缓存目录。
